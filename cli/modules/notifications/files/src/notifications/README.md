# Notifications Module

> **Plug-and-play push notification layer for React Native / Expo.**
> Permissions, Android heads-up channels, remote push in foreground / background / killed states, tap routing, and local trigger scheduling — behind one import path, with two integration points and one file to configure.

**Transport only.** This module _moves_ notifications. It contains no features and knows nothing about what any given notification means. Nothing in it names a product concept: the parts you edit are `config.ts` and the token adapter, `useNotificationSync.ts`.

Generated by `create-expo-boilerplate add notifications`.

## Scope — what this owns and what it does not

| Concern                                                | Owner                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| Asking for permission, and reading the real state back | **this module**                                              |
| Creating and versioning Android channels               | **this module**                                              |
| Acquiring the FCM token and handing it to your backend | **this module**                                              |
| Receiving remote messages in every app state           | **this module**                                              |
| Turning a payload into an allowlisted route            | **this module**                                              |
| Handing local triggers to the OS                       | **this module**                                              |
| Deciding **what** to notify about, and **when**        | **your feature code**                                        |
| Firing a recurring notification on a schedule          | **your backend** (see [Backend contract](#backend-contract)) |

The last two rows are the boundary that keeps this portable. A feature that needs local notifications builds its own triggers and calls `scheduleLocalNotifications` — the module takes fully-resolved instants and has no opinion on how they were derived.

**The dependency arrow points one way.** Feature code imports `@/notifications`; nothing here imports feature code. If you ever need an import pointing outward from this folder, something has been put on the wrong side of the line.

```
│  └────────────────────────────────────────────┘          │
└──────────────────────────────────────────────────────────┘
                          │
          ┌───────────────▼──────────────────┐
          │     NotificationProvider          │
          │  • every listener, once           │
          │  • cold-start route queue         │
          │  • token registration             │
          │  • NEVER prompts                  │
          └───────────────┬──────────────────┘
                          │
          ┌───────────────▼──────────────────┐
          │      permissionState / routing    │
          │              (PURE, tested)       │
          └───────────────┬──────────────────┘
                          │
          ┌───────────────▼──────────────────┐
          │           service.ts              │
          │  the ONLY file importing          │
          │  notify-kit + firebase/messaging  │
          └───────────────┬──────────────────┘
                          │
             NotifyKit (draws, schedules)
             Firebase Messaging (delivers)
```

**The stack.** `@react-native-firebase/messaging` receives messages but draws nothing — no channels, no foreground presentation, no local scheduling. `react-native-notify-kit` supplies all of that. Both are needed; neither is sufficient.

Why this pairing rather than `expo-notifications`: on iOS `expo-notifications` yields an **APNs** token, and FCM cannot send to an APNs token. Using it would force the backend to add a separate direct-APNs sender. This stack keeps one FCM token on both platforms and leaves the existing Firebase send path untouched. The trade-off — NotifyKit is a community fork of the archived Notifee — is addressed in [Replacing the stack](#replacing-the-stack).

## Native setup

> The generator applied everything in this section. It is documented so you know what each piece is for, and what to check when something silently fails.

### Dependencies

```bash
yarn add @react-native-firebase/app @react-native-firebase/messaging react-native-notify-kit
```

### `app.config.ts`

```ts
plugins: [
  '@react-native-firebase/app',
  '@react-native-firebase/messaging',
  'react-native-notify-kit',
  './plugins/withAndroidDefaultNotificationChannel',
];
```

Drop `google-services.json` and `GoogleService-Info.plist` in, and upload the APNs `.p8` key to **Firebase console → Project settings → Cloud Messaging** so FCM can relay to iOS.

**iOS also needs this in `app.config.ts`, and no plugin adds it for you:**

```ts
ios: {
  entitlements: { 'aps-environment': 'development' },
  infoPlist: { UIBackgroundModes: ['remote-notification', /* … */] },
}
```

This is the easiest thing in the whole setup to miss, because nothing fails loudly. The `@react-native-firebase/messaging` config plugin is **Android-only** — its source contains a bare `// iOS` comment with no mods beneath it — and NotifyKit's iOS plugin only builds the opt-in Notification Service Extension. Neither touches entitlements.

Without `aps-environment` the app cannot register with APNs, so `getToken()` returns `null`, no token is ever sent to the backend, and every iOS push is dropped with nothing in the logs to say why.

`development` is correct even for App Store builds — Xcode rewrites it to `production` when it archives a release, and hardcoding `production` breaks push on debug builds.

Two things this does _not_ do: it does not enable the capability on the Apple Developer portal (EAS handles that during credentials setup, or tick it on the App ID by hand), and it does not survive being added by hand in Xcode — `ios/` is gitignored in a CNG project, so a manual capability toggle is wiped by the next `expo prebuild`. It has to live in `app.config.ts`.

Verify without regenerating the native project:

```bash
npx expo config --type prebuild --json | jq '.ios.entitlements, .ios.infoPlist.UIBackgroundModes'
```

`POST_NOTIFICATIONS` (Android 13+) is added by the NotifyKit plugin. It deliberately does **not** add `SCHEDULE_EXACT_ALARM` or `USE_FULL_SCREEN_INTENT` — leave both off; see [Known limits](#known-limits) and [Gotcha 3](#3-exact-alarms-will-be-refused-and-the-throw-disappears).

The second plugin, `withAndroidDefaultNotificationChannel`, is **not optional** — without its `tools:replace` the Android build fails outright. See [Gotcha 4](#4-the-manifest-meta-data-collides-with-rnfirebase).

## Integration points

There are two, plus the banner.

### 1. Entry point — `index.ts`

```ts
import '@/notifications/setup'; // side effect — MUST be module scope
```

`setup.ts` registers the background handlers and creates the channels.

A background message spins up the JS runtime **headless**, with no component tree. A handler registered inside a React component is attached too late by definition.

On Android 13+ the OS **refuses to show the notification prompt until the app has at least one channel**, so a permission request that beats channel creation silently resolves as denied with no dialog. That bug presents as "permissions are broken", not as "channels are missing" — which is why channels are created at the entry rather than lazily.

### 2. Providers — `src/providers/AppProviders.tsx`

```tsx
<APIProvider>
  <NotificationRoot>{children}</NotificationRoot>
</APIProvider>
```

`NotificationRoot` reads the session from `useIsLoggedIn()` and navigates through `navigation.ts`. It sits inside `APIProvider` because token registration is a mutation, and around the navigation root so the navigator exists by the time a queued cold-start route is delivered.

### 3. The permission screen

```tsx
<NotificationPermissionBanner />
```

Mount it on whichever screen is allowed to ask, always tied to an explicit user action. Which channel its `channel-blocked` state checks, and which channel Settings deep-links to, is `PRIMARY_CHANNEL_ID` in `config.ts`.

## Configuration reference

Everything project-specific lives in `config.ts`. Nothing outside it names a channel, a payload type, or a route.

| Constant                   | What it decides                                                                                                                                                |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NOTIFICATION_TYPES`       | The payload vocabulary. `NotificationType` is derived from it, so adding a type is one edit.                                                                   |
| `CHANNELS` / `CHANNEL_IDS` | Android channels, their importance, sound and vibration.                                                                                                       |
| `DEFAULT_CHANNEL_ID`       | Fallback when a payload carries no `channel_id`. **Must match the manifest plugin.**                                                                           |
| `PRIMARY_CHANNEL_ID`       | The channel whose mute state raises `channel-blocked`, and where Settings deep-links.                                                                          |
| `DEPRECATED_CHANNEL_IDS`   | Retired channel ids, deleted at startup after a version bump.                                                                                                  |
| `ROUTE_BY_TYPE`            | `type` → in-app route. `null` means "just open the app". Paths work with both Expo Router and React Navigation (resolved through `src/navigation/linking.ts`). |
| `TYPES_WITH_ID`            | Types whose payload `id` is appended to the route as `?id=…`.                                                                                                  |
| `TYPE_BY_PAYLOAD_VALUE`    | Backend wire value → internal type. Matched case-insensitively.                                                                                                |
| `AUTHENTICATED_ROUTES`     | Routes dropped when logged out, so a cold start does not flash a gated screen.                                                                                 |
| `CLEAR_BADGE_ON_OPEN`      | Clear the app icon badge when the app opens or returns to the front. See [App icon badge](#app-icon-badge).                                                    |
| `ANDROID_DISPLAY_STRATEGY` | `fcm-draws` (default) or `app-draws`. See [FCM Mode](#switching-to-fcm-mode).                                                                                  |

### Channel ids carry a version suffix, and it is not decoration

Once a channel exists on a device, Android freezes everything about it except the name and description — importance, sound and vibration cannot be changed for as long as the app stays installed. To change a frozen property: bump the suffix (`general.v1` → `general.v2`), add the old id to `DEPRECATED_CHANNEL_IDS`, and update the backend's `channel_id`. This resets any per-channel preference the user had set, so do it deliberately rather than routinely.

## Permission policy

**`NotificationProvider` never prompts.** It reads permission and exposes a request function, but the only consumer of that function is `useNotificationPermission`. Mounting that hook is what makes a screen able to prompt — which keeps "never on mount, only on a tap" a structural property rather than a convention someone breaks in six months.

Out of the box one screen mounts it, through `NotificationPermissionBanner`: Settings. The banner is the only thing that prompts, and only on a deliberate tap of its CTA. Adding another screen is a decision, not a detail — the iOS prompt is spent permanently on the first refusal.

If you add in-app notification preferences (a switch for "marketing", a reminders toggle), keep them separate from the device grant: the switch holds the account's preference, the banner reports whether the OS will deliver at all.

The prompt is spent on an explicit user action, never on mount. A prompt the user did not ask for is the one they deny, and on iOS a denial is permanent.

### The five states

| State             | Meaning                                                          | CTA                   |
| ----------------- | ---------------------------------------------------------------- | --------------------- |
| `granted`         | Delivering.                                                      | _(banner hidden)_     |
| `undetermined`    | Never asked.                                                     | Prompt                |
| `denied`          | Refused, prompt still reachable (Android, before 2nd refusal).   | Prompt                |
| `blocked`         | Refused, **prompt gone forever**.                                | Open Settings         |
| `channel-blocked` | **Android.** App permission granted, `PRIMARY_CHANNEL_ID` muted. | Open channel settings |

The last two are why the union exists rather than a boolean:

- **`blocked`** — `requestPermission()` is a no-op once iOS has recorded a denial. A CTA that calls it renders a button that does nothing, which reads as a broken app rather than a reversible setting.
- **`channel-blocked`** — every permission API reports success and Android drops every notification on that channel anyway. Nothing surfaces it except an explicit `isChannelBlocked()` check.

Status is re-read on `AppState → active` **and** on screen focus, which is what closes the loop when someone leaves for Settings, flips the switch, and comes back.

## Delivery matrix

| App state      | What the OS does                                                          | What the module does                                                                      |
| -------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| **Foreground** | Nothing is drawn, either platform. FCM hands the message to JS and stops. | `onMessage()` → `displayNotification()`. **Without this a foreground push is invisible.** |
| **Background** | System tray, drawn by FCM from the `notification` block.                  | `onNotificationOpenedApp()` for the tap. Background handler for data only.                |
| **Killed**     | Delivered only if the payload has a display block.                        | `getInitialNotification()` on boot → queued until the router is ready.                    |

### Remote flow, by app state

```
backend ──► FCM ──► device
                     │
     ┌───────────────┼────────────────────┐
 FOREGROUND     BACKGROUND             KILLED
     │               │                    │
 onMessage()   FCM draws tray        FCM draws tray
     │         from `notification`   from `notification`
     ▼               │                    │  ⚠ data-only DROPPED
 notifee.displayNotification              │
     │               │                    │
     ▼               ▼                    ▼
    tap             tap                  tap → cold launch
     │               │                    │
 onForegroundEvent   onNotificationOpenedApp   getInitialNotification()
     │               │                    │  parked until router ready
     └───────────────┴────────────────────┘
                     ▼
           routing.ts allowlist → router.push
```

Nothing in the foreground column is free: **FCM draws nothing while the app is open**, on either platform. The `displayNotification` call is the only reason a foreground push is visible.

### iOS: who owns the tap

On iOS both NotifyKit and React Native Firebase Messaging want to be
`UNUserNotificationCenter.delegate`, and NotifyKit wins — it re-chains itself in
on every `didBecomeActive`, while Firebase installs itself once at launch.

With NotifyKit's `handleRemoteNotifications` left at its default of `true`, it
then **claims** an FCM tap rather than passing it down the chain whenever it has
nothing below it to pass to. Firebase never hears about the notification, so
`onNotificationOpenedApp()` and `getInitialNotification()` both stay silent —
and NotifyKit's own `getInitialNotification()` returns `null` for it too,
because the payload carries no NotifyKit-authored id for its native store to
release. The push opens the app and lands nowhere, in **both** background and
killed states. Android has no delegate chain and is unaffected, which is exactly
how this presents in QA: "works on Android, does nothing on iOS".

`backgroundHandler.ts` sets `handleRemoteNotifications: false` at module scope —
the earliest JS in the app — so remote push has one owner on iOS (Firebase) and
local triggers keep theirs (NotifyKit).

### NotifyKit's two press channels both land too early

NotifyKit splits presses across a foreground and a background channel by the app
state at the instant it hands the event to JS. Both instants fall **before**
`NotificationProvider` exists, for two different reasons:

- **App backgrounded.** iOS delivers the response while the app is still
  `Inactive` — including the tap that brings a backgrounded app forward — so the
  press goes to the _background_ channel. The app is never relaunched, and
  `getInitialPayload()` already ran this launch.
- **App killed.** iOS delivers the response before the bundle has loaded, so
  NotifyKit buffers the event natively. When the first JS listener attaches and
  the buffer flushes, NotifyKit **re-reads the app state as it flushes** — the
  app is `Active` by then, drawing the splash, so a press queued from a _killed_
  app comes out on the _foreground_ channel.

The second one is the trap. A foreground subscription made from the provider is
attached several seconds after that flush — behind storage, i18n and the rest of
`useAppBootstrap` — so it misses the launch it exists for, and the press is dropped
with nothing listening.

`backgroundHandler.ts` therefore subscribes to **both** channels at module
scope, being the first app code in the bundle, and funnels every press into
`pendingPress.ts`. That parks the payload until `onNotificationPress` drains it
for the provider. Since one tap can now arrive by two paths depending on who
owned the notification natively, the provider ignores a repeat of the same route
within a two-second window.

### One library must not be able to hang the other

NotifyKit's iOS `getInitialNotification()` only releases its stored notification
once a native `didFinishLaunching` observer has marked it _gathered_; until then
it parks the promise's resolver and returns nothing — and if that observer never
runs, the promise **never settles**. Awaited in sequence ahead of Firebase, that
alone kills cold-start routing for remote pushes as well.

`getInitialPayload()` reads both sources in parallel and puts a 2s timeout on the
NotifyKit half. The stores are one-shot and independent, so reading both costs
nothing and only one of them ever holds the tap.

### Cold-start routing needs a queue

A tap on a killed app resolves its payload during the first render pass — long before storage, i18n, the splash, and route guards have settled. Pushing immediately either throws or lands on a guarded route that bounces the user straight back off.

`NotificationProvider` parks the route in a ref and flushes it once the navigator exists. If the target is gated and the user is not signed in, it is **dropped rather than queued** — it will not become deliverable this launch, and holding it would fire it the moment they signed in for an unrelated reason.

## Heads-up

Both halves are required. Neither alone is sufficient.

|         | Requirement                                        | Set in       |
| ------- | -------------------------------------------------- | ------------ |
| Android | Channel `importance: HIGH`                         | `config.ts`  |
| Android | Message `priority: "high"` + matching `channel_id` | Backend      |
| iOS     | `apns-priority: 10`, `apns-push-type: alert`       | Backend      |
| iOS     | `foregroundPresentationOptions: { banner, list }`  | `service.ts` |

If the backend cannot send `channel_id`, `plugins/withAndroidDefaultNotificationChannel` writes a manifest fallback. **Its `CHANNEL_ID` must match `DEFAULT_CHANNEL_ID` in `config.ts`** — if they drift, Android invents a low-importance "Miscellaneous" channel and every remote notification silently loses heads-up, with nothing in the logs.

## Local scheduling

A general capability of the module, available to any feature that needs the **device** to fire something without a network round trip.

```ts
await scheduleLocalNotifications(triggers, {
  channelId: 'general.v1',
  cancelPrefix: 'digest-',
  data: { type: 'general' },
});
```

`scheduleLocalNotifications` clears every trigger matching `cancelPrefix`, then schedules the ones you hand it. Prefix-matched rather than `cancelAllNotifications`, so one feature's re-sync cannot wipe another's — give each feature its own prefix, and include the separator (`'digest-'`, not `'digest'`) or the match will also claim ids like `digestive-3`.

Passing an **empty array cancels everything under the prefix and schedules nothing**, which is what lets an on/off toggle behave as a delete with no second code path.

A `LocalTrigger` is domain-free: an id, an epoch-ms timestamp, a title and a body. Working out _which_ instants to fire at is your feature's job — the module has no notion of weekdays, wall-clock strings, or recurrence rules beyond the weekly repeat it hands the OS.

```ts
interface LocalTrigger {
  id: string; // must start with your cancelPrefix
  timestamp: number; // epoch ms of the first occurrence
  title: string;
  body: string;
}
```

### When to reach for this, and when not to

Local scheduling **works offline**, has no timezone problem — the device already knows where it is — and needs no token, no registration round trip, and no server-side fan-out job.

What it costs:

- **Delivery is inexact on Android** — measured ~69s late, see [Known limits](#known-limits).
- **Changes need an app open.** A schedule edited server-side does not reach a device until that device next launches and re-syncs.
- **No server-side visibility.** Nobody can tell whether anything was actually delivered.

For anything recurring that the product cares about — a daily nudge, a streak reminder, a digest — those three costs usually push the decision to **remote push fired by the backend** instead. That is usually the better arrangement; see [Backend contract](#backend-contract).

## App icon badge

By default the badge is cleared whenever the app opens or comes back to the front (`CLEAR_BADGE_ON_OPEN` in `config.ts`) — opening the app means the user has seen what was waiting.

When the badge is a real count (unread messages, pending tasks), turn that off and keep the number in sync yourself:

```ts
import { setBadgeCount } from '@/notifications';

setBadgeCount(unreadCount); // wherever the count changes
```

and have the backend send the same number in remote pushes, so it is right while the app is closed:

```jsonc
"apns": { "payload": { "aps": { "badge": 3 } } }
```

| Platform | What the badge is                                                                                                      |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| iOS      | Exactly the number you set (or `aps.badge`). `0` hides it.                                                             |
| Android  | Launcher-dependent. Most show a dot per notification on their own; numeric badges only on launchers that support them. |

`setBadgeCount`, `getBadgeCount` and `clearBadge` never throw — a badge is decoration.

## Backend contract

**One send path.** Firebase Admin SDK, FCM registration tokens, both platforms, iOS via Firebase's APNs relay.

### Token registration

```jsonc
// POST <your --token-endpoint>     (Authorization: Bearer <access token>)
{ "token": "fMEr...", "platform": "ios" }
```

An FCM registration token on **both** platforms — iOS included, because Firebase relays to APNs on the backend's behalf. That is what lets the server keep one send path and one credential set.

The backend keys the token off the bearer token's user. Change the body in `useNotificationSync.ts` if your API expects a different shape. The request is sent with `silent: true`, so a failure never shows the user an error toast.

**There is no revoke call.** The backend should clear the token as part of its logout endpoint, so signing out is what stops delivery. The client also does _not_ delete the local FCM token — deleting it would force FCM to mint a fresh one on next sign-in for no benefit, since the backend has already detached the old one, and re-registering the same token against the new user is both correct and cheaper.

Called on login, on token refresh, and when permission transitions to granted — never at startup. A token acquired before the user agrees is one the backend will send to and the OS will silently discard, which presents as a broken backend rather than a missing permission.

### Payload

```jsonc
{
  "message": {
    "token": "...",
    "notification": { "title": "New sign-in", "body": "Your account was used on a new device." },
    "data": { "notification_type": "ACCOUNT_ALERT", "id": "482" }, // strings only
    "android": {
      "priority": "high",
      "notification": { "channel_id": "general.v1" },
    },
    "apns": {
      "headers": { "apns-priority": "10", "apns-push-type": "alert" },
      "payload": { "aps": { "sound": "default" } },
    },
  },
}
```

> **Killed-state rule.** Any push that must survive a force-quit app needs a **display block** — `notification` on FCM, `aps.alert` on APNs. Android drops data-only messages to a killed app entirely: nothing displays and no code runs. Put routing info in `data` _alongside_ it, never instead of it.

`data.route` is **ignored by design**. Routes come from the client's `ROUTE_BY_TYPE` allowlist, so a malformed or hostile payload can at worst open the app rather than deep-link anywhere it likes.

### Recurring and scheduled pushes are the backend's job

Anything that fires on a schedule — a daily reminder, a weekly digest, a streak nudge — is sent by the backend as an ordinary remote push. **The device schedules nothing for it and stores no copy of the schedule.** The client is a rendering and routing layer; every decision about _whether_ and _when_ lives server-side.

| Question                                      | Owner                                  |
| --------------------------------------------- | -------------------------------------- |
| What the schedule **is** — time, days, on/off | **Backend**                            |
| **When** it fires                             | **Backend** — the scheduler            |
| Which **timezone** that means                 | **Backend**                            |
| Which **screen** a tap opens                  | **Client** — `ROUTE_BY_TYPE` allowlist |

What a scheduler has to get right:

1. **Know each user's timezone** (IANA, e.g. `Asia/Kolkata`). A stored time like `"7:25 pm"` is a bare wall clock with no zone attached — without the zone, it fires at 7:25 pm _somewhere else_. Either add a `timezone` field to the token endpoint or source it from the user profile; this is the single most common reason a scheduled push lands at the wrong hour.
2. **Scan on a cadence.** Minute-granularity times mean the job runs at least once a minute, or buckets by minute and runs per bucket.
3. **Match in the user's local time**, not the server's:

   ```
   for each active schedule:
       tz    := that user's timezone
       local := now() in tz
       if weekday(local) ∈ schedule.days
          and hh:mm(local) == schedule.time:
              send to every device token for that user
   ```

4. **Fan out to all of a user's devices.** One person, several handsets — each needs its own send.
5. **De-duplicate.** Record `(schedule_id, local_date)` after sending. Without it, an overlapping or retried cron run sends the same push twice.
6. **Handle DST.** A 2:30 am schedule does not exist on a spring-forward date and happens twice on a fall-back date. Pick a rule — skip and log, or fire once — rather than letting the library decide silently.
7. **Send an explicit `channel_id`.** Without it Android falls back to the manifest default, and the user loses the ability to mute one category separately from another.

## The Android duplicate-notification trap

Under the default `ANDROID_DISPLAY_STRATEGY = 'fcm-draws'`, FCM has **already drawn** the tray notification by the time `setBackgroundMessageHandler` runs. Calling `displayNotification()` or `handleFcmMessage()` there draws a **second one** — every push arrives twice.

Both halves look correct in isolation, which is why the strategy is a `config.ts` flag branched on in `backgroundHandler.ts` rather than a comment someone deletes.

## Gotchas that will cost you an afternoon

Every one of these was hit during implementation. All of them fail **silently**.

### 1. Anything reading notification context must be a CHILD of the provider

The component that renders `<NotificationProvider>` cannot also call a hook that consumes the context — a component never sees a context it provides. Put the consumer in a null-rendering child instead:

```tsx
<NotificationProvider …>
  <SomeContextConsumer />   {/* renders null */}
  <Navigator />
</NotificationProvider>
```

Symptom: `useNotificationContext must be used within <NotificationProvider>` from a component that visibly _is_ inside it.

### 2. Never put an unstable function in a scheduling effect's deps

A translate helper that returns a **new closure every render** in an effect's dependency array re-runs that effect on every render — and since `scheduleLocalNotifications` opens by cancelling everything under its prefix, overlapping runs delete the triggers the previous run just created. **Nothing ever survives to fire.**

Depend on a stable value (`i18n.language`, a string) and call a module-level `translate()` instead. Any feature that wires its own scheduling effect must check this — it presents as "the notifications just don't work", with everything else looking correct.

### 3. Exact alarms will be refused, and the throw disappears

Android 12+ gates exact alarms behind `SCHEDULE_EXACT_ALARM`. NotifyKit **throws** when it is missing, and if the caller used `void schedule(...)` the rejection vanishes into a floating promise.

The module uses `alarmManager: { type: AlarmType.SET_AND_ALLOW_WHILE_IDLE }` — inexact, no permission, still fires in Doze. Not the deprecated `allowWhileIdle: true`, which maps to an _exact_ alarm.

Check the grant state with `dump()` below: `android.alarm` is `0` when denied.

### 4. The manifest meta-data collides with RNFirebase

`@react-native-firebase/messaging` ships its own `default_notification_channel_id` with an **empty** value. Two declarations of the same `meta-data` name is a hard merge failure at `processDebugMainManifest`. The config plugin adds `tools:replace="android:value"` for exactly this.

### 5. Use the modular Firebase API

RNFirebase v22 deprecated namespaced `messaging()`; the next major removes it. This module uses `getMessaging(getApp())` throughout, resolved through a **lazy getter** — `getApp()` throws if Firebase has not initialised, and `service.ts` is imported during the first render pass.

## Testing & debugging

The pure modules, the service boundary and `NotificationProvider` are covered, with no device required. The provider tests mock `service.ts` whole and drive each listener directly: permission re-reads, the never-prompts rule, token registration (only signed in AND granted), cold-start and running taps, route gating and de-duplication, foreground display, and the badge.

```bash
yarn test src/notifications
```

NotifyKit ships ESM and a native module, so `jest.setup.ts` maps it to the package's own `jest-mock`, which re-exports every enum as a real value. Firebase is stubbed to only the **modular** surface `service.ts` calls — the namespaced form is deliberately absent, so a regression to it fails loudly in tests rather than shipping a deprecation warning.

### Inspecting a running app

Almost every failure here is silent, and Metro's Hermes runtime has no `require`, so there is no way to interrogate the module from outside without an explicit handle. `service.ts` installs one under `__DEV__`:

```js
await globalThis.__notifications.dump();
// {
//   authorizationStatus: 1,                    // 1 = AUTHORIZED
//   android: { alarm: 0 },                     // 0 = exact-alarm DENIED
//   scheduledTriggerIds: [],                   // locally scheduled triggers
//   primaryChannel: { importance: 4 },         // PRIMARY_CHANNEL_ID, 4 = HIGH
//   primaryChannelBlocked: false,
// }

await globalThis.__notifications.fireTestNotification(); // bypasses scheduling
await globalThis.__notifications.scheduleLocalNotifications(triggers, opts);
```

Read it top-down: permission → channel → scheduled ids. The first row that looks wrong is the cause. Stripped from release builds.

## Switching to FCM Mode

`ANDROID_DISPLAY_STRATEGY = 'app-draws'` makes NotifyKit draw every notification in every state, identically, with rich styles (BigPicture, Inbox, progress) available on remote pushes.

It requires:

1. Backend sends **data-only** payloads built with `buildNotifyKitPayload()` from `react-native-notify-kit/server`.
2. An iOS Notification Service Extension — generated by the config plugin via `ios: { notificationServiceExtension: true }`.

The client code already branches for it; `backgroundHandler.ts` calls `handleFcmMessage()` under that flag. Worth revisiting only if rich remote notifications become a requirement.

## Replacing the stack

NotifyKit is a community fork of Notifee, archived by Invertase in April 2026. It is actively maintained, carries the full upstream history, has migrated to the New Architecture (which archived Notifee has not — that alone makes it the only workable option on RN 0.86), and is the successor Invertase name. But it is **one maintainer**.

The mitigation is structural, not hopeful: **every NotifyKit and Firebase call lives in `service.ts`.** If the fork stalls, migrating to `expo-notifications` means rewriting that one file and adding a direct APNs sender on the backend — the same work as doing it today, deferred at no extra cost. Nothing else in the module knows which library is underneath.

Keep it that way: **never import `react-native-notify-kit` or `@react-native-firebase/messaging` outside `service.ts`, `channels.ts` and `backgroundHandler.ts`.**

## Verification & troubleshooting

### Checklist

Work down the list — each step only makes sense once the one above it passes.

```bash
# 1. Native config actually landed
npx expo config --type prebuild --json | jq '.ios.entitlements, .ios.infoPlist.UIBackgroundModes'

# 2. It builds
npx expo prebuild --clean && yarn ios:development     # and android:development

# 3. Types and tests
yarn type-check && yarn test src/notifications
```

Then on a **physical iPhone** and an Android device or Play-Services emulator:

| #   | Check                                                 | Pass looks like                                               |
| --- | ----------------------------------------------------- | ------------------------------------------------------------- |
| 1   | Launch the app                                        | Android: channels exist under Settings → Apps → Notifications |
| 2   | `await globalThis.__notifications.dump()`             | `authorizationStatus`, channel present, no throw              |
| 3   | Visit the permission screen, tap the CTA              | OS prompt appears (not a silent no-op)                        |
| 4   | Grant, then `dump()` again                            | `authorizationStatus: 1`                                      |
| 5   | Check your backend                                    | A token arrived for this user                                 |
| 6   | Send a test push, **app foregrounded**                | Banner appears — proves `onMessage` → `displayNotification`   |
| 7   | Send one, **app backgrounded**                        | Tray notification, heads-up                                   |
| 8   | Tap it                                                | Lands on the route from `ROUTE_BY_TYPE`, not the home screen  |
| 9   | **Force-quit**, send one, tap it                      | App cold-starts and still lands on the right route            |
| 10  | Android: mute the primary channel in Settings, reopen | Banner shows the `channel-blocked` copy                       |

Step 9 is the one people skip and the one that breaks — it exercises the cold-start route queue.

### Symptoms

Everything here fails silently, so match on symptom:

| Symptom                                                  | Likely cause                                                                                                                 |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `getToken()` returns `null` on iOS                       | `aps-environment` entitlement missing from `app.config.ts`, or no APNs key in the Firebase console                           |
| No token on iOS, simulator only                          | Expected — simulators have no APNs. Use a device.                                                                            |
| Permission prompt never appears on Android 13+           | `configureNotifications()` ran after the request, or not at all — no channel means no prompt                                 |
| Android build fails at `processDebugMainManifest`        | The channel plugin is missing from `app.config.ts`                                                                           |
| Every push arrives **twice** on Android                  | The background handler is drawing on top of FCM — see [the duplicate trap](#the-android-duplicate-notification-trap)         |
| Push arrives in background but **nothing** in foreground | Normal OS behaviour — you removed or broke the `displayNotification` call                                                    |
| Nothing at all when the app is force-quit                | Payload is data-only. Android drops those to a killed app; add a `notification` block                                        |
| Tap opens the app but never navigates                    | `type` is missing from `data`, or absent from `TYPE_BY_PAYLOAD_VALUE` — it degraded to `general`                             |
| Tap navigates, except from a cold start                  | Something reads notification context above the provider, or the route is in `AUTHENTICATED_ROUTES` and auth had not resolved |
| No heads-up, notifications land silently                 | Channel importance below HIGH, **or** the backend omitted `priority: "high"` — both halves are required                      |
| Locally scheduled triggers vanish immediately            | An unstable dependency in the scheduling effect — [Gotcha 2](#2-never-put-an-unstable-function-in-a-scheduling-effects-deps) |
